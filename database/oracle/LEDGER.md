# Внутренний финансовый API Oracle

`sql/40_ledger.sql` создаёт `PROXIMA_OWNER.PKG_LEDGER`: спецификация контракта расположена перед телом. Схема ER не меняется. Пакет **не предоставляется PROXIMA_APP или PUBLIC**. Каждый вызов дополнительно требует `SESSION_USER` SYS либо PROXIMA_OWNER. Переданный `p_owner_user_id` — объект действия доверенного оператора БД, а не подтверждение личности пользователя. Подключение интерфейса к этим операциям требует отдельной серверной аутентификации и авторизации.

Для ручного сценария администратор создаёт владельца с `account_status='Active'`. Это явный контракт данного внутреннего API: существующий C# не определяет перечисление статусов Oracle, другие значения отклоняются. Данные учётных записей и пароли пакет не создаёт и не проверяет.

| Процедура | Параметры в порядке вызова |
|---|---|
| `create_portfolio` | owner RAW, name VARCHAR2, base_currency VARCHAR2, id OUT RAW |
| `post_cash` | owner RAW, portfolio RAW, type VARCHAR2, trade_date TIMESTAMP WITH TIME ZONE, amount NUMBER, currency VARCHAR2, fee_amount NUMBER, id OUT RAW, operation_order NUMBER DEFAULT 0 |
| `post_trade` | owner RAW, portfolio RAW, instrument RAW, type VARCHAR2, trade_date TIMESTAMP WITH TIME ZONE, quantity NUMBER, price NUMBER, fee_amount NUMBER, id OUT RAW, operation_order NUMBER DEFAULT 0 |
| `update_transaction` | owner RAW, transaction RAW, trade_date TIMESTAMP WITH TIME ZONE, quantity NUMBER, price NUMBER, gross_amount NUMBER, fee_amount NUMBER, operation_order NUMBER DEFAULT NULL |
| `remove_transaction` | owner RAW, transaction RAW |
| `get_balances` | owner RAW, portfolio RAW, result OUT SYS_REFCURSOR |
| `get_realized_pnl` | owner RAW, portfolio RAW, result OUT SYS_REFCURSOR |

Полные имена параметров содержатся в спецификации. Типы и валюту существующей операции `update_transaction` не меняет; для исправления типа требуется удалить и создать операцию в одной внешней транзакции. Отрицательная история при промежуточном удалении отклоняется: групповые исправления пока не поддерживаются.

`get_balances` возвращает `currency, cash_balance`; валюты без операций не создаются с искусственным нулевым остатком. `get_realized_pnl` возвращает одну строку на продажу: `transaction_id, asset_id` (строки RAWTOHEX), `currency, trade_date, net_proceeds, fifo_cost, realized_pnl`. Результаты остаются в валюте инструмента; сумма разных валют не вычисляется. Оба чтения также блокируют портфель до завершения внешней транзакции, чтобы согласоваться с писателями.

`Deposit` и `Withdrawal` записываются без актива, с нулевыми количеством и ценой, положительной `gross_amount`. `Buy` и `Sell` требуют положительных количества и цены; валюта берётся из справочника инструмента. `gross_amount=ROUND(quantity*price,10)`. Комиссия всегда явно передаётся, неотрицательна и выражена в той же валюте. Покупка списывает gross+fee, продажа зачисляет gross-fee, пополнение зачисляет gross-fee, вывод списывает gross+fee. Налог пока явно равен нулю: это техническая граница учётного API, а не налоговый расчёт.

Каждая мутация блокирует строку портфеля `SELECT FOR UPDATE` до чтения и изменения его истории. Затем полностью воспроизводит операции по `trade_date,operation_order,id`, проверяя денежный остаток каждой валюты и количество каждого актива после каждого события. Для одного момента задаётся явный operation_order: целое число от 0 до 999999999999999999. Совпадающая пара (момент, порядок) внутри портфеля отклоняется с -20103, включая одинаковые UTC-моменты с различным часовым поясом. Проверка выполняется под блокировкой до INSERT/UPDATE; replay повторно проверяет историю. Разные порядки разрешают события в один момент без молчаливой перестановки. Короткие позиции и отрицательные денежные остатки запрещены. Исправление прошлого может быть отклонено из-за последующего события.

FIFO реализуется временной PL/SQL-коллекцией лотов. Комиссия покупки включается в стоимость лота; продажа потребляет старейшие лоты, её комиссия уменьшает выручку. `assets.quantity` и `average_buy_price` пересчитываются; последняя означает среднюю стоимость **оставшихся FIFO-лотов** с комиссиями. При нулевой позиции цена NULL. `current_price` не подменяется ценой сделки. Рыночные цены, исторические курсы и ML не используются и не выдумываются.

Каждая мутация устанавливает savepoint и при любой ошибке, включая ошибку аудита, откатывает все собственные изменения, сохраняя более раннюю работу вызывающей транзакции. Пакет не делает COMMIT. Вызывающий оператор обязан явно выполнить COMMIT либо ROLLBACK; успешные операции удерживают блокировки. Журнал хранит тип действия, субъекта, время, портфель и JSON состояния операции до/после; удаление операции не удаляет журнал. Прямой DML администратора обходит эти гарантии, поэтому для финансового сценария следует пользоваться пакетом.

При установке из SYS используется `ALTER SESSION SET CURRENT_SCHEMA=PROXIMA_OWNER`, затем `@40_ledger.sql`; проверяется `ALL_ERRORS` и статус PACKAGE/BODY. Разблокировать владельца для этого не требуется. Тестовые числовые цены в отдельном SQL-сценарии служат проверке арифметики и не являются рыночными данными.

Начальные остатки с неизвестной себестоимостью, FX, налоги, импорт, архивирование/удаление портфеля, отчёты и клиентская авторизация пока не реализованы. Все остатки этого среза начинаются с нуля и выводятся только из поддерживаемых событий. Полный replay и линейный обход FIFO-лотов при продажах ориентированы на проверку корректности небольшого сценария: производительность на 100 000 событий ещё не измерена, масштабируемость не заявляется.

Параметр p_operation_order добавлен последним после OUT id в post_cash/post_trade и по умолчанию равен 0; прежние вызовы совместимы. В update_transaction последний параметр по умолчанию NULL означает сохранить существующий порядок. Обе аналитические FIFO-последовательности используют тот же порядок, что и replay; аудит сохраняет operation_order до/после изменения.
