# Серверная аутентификация

`23_auth.sql` создаёт `PKG_AUTH AUTHID DEFINER`. Порядок установки: PKG_PASSWORD, таблица auth_sessions, PKG_AUTH, затем из SYS `CREATE CONTEXT PROXIMA_CTX USING PROXIMA_OWNER.PKG_AUTH`. Нужна прямая привилегия владельца на SYS.DBMS_CRYPTO. Установщик проверяет ALL_ERRORS; разрешения прикладной учётной записи выдаются отдельно.

Контракт спецификации:

- `register_user(login,password,display_name,user_id OUT RAW)` создаёт только PrivateInvestor; логин нормализуется LOWER(TRIM), длина 3–64, символы a–z, 0–9, `_`, `.`, `-`; отображаемое имя обязательно, не длиннее 255 символов.
- `login(login,password,token OUT VARCHAR2,user_id OUT RAW,role OUT VARCHAR2)` выдаёт случайный 32-байтовый токен в виде 64 hex-символов, действующий 8 часов. В таблице хранится только SHA256 исходных случайных байтов. Пароли обрабатывает PKG_PASSWORD; значения пароль/токен/хеш не попадают в аудит.
- `logout(token)` автономно отзывает сессию; повторный, отсутствующий или некорректный токен не раскрывает сведения о сессиях.
- `require_user(token) RETURN RAW`, `require_admin(token) RETURN RAW`, `user_role(token) RETURN VARCHAR2` проверяют срок, отзыв и актуальное состояние пользователя. Допустимые роли: PrivateInvestor, FinancialConsultant, Admin; для доступа требуется Active. Остальные статусы и роли отклоняются.
- `begin_request(token)` сначала очищает прежний TOKEN_HASH в защищённом контексте PROXIMA_CTX, проверяет токен, затем записывает только его хеш. `current_user_id RETURN RAW` каждый раз повторно читает сессию и пользователя; блокировка/отзыв действуют также для ранее установленного контекста. При работе с пулом каждый прикладной вызов обязан начинаться с begin_request и не принимать actor ID клиента как идентификатор пользователя.
- `provision_admin(login,password,display_name,user_id OUT RAW)` разрешён только SESSION_USER SYS/PROXIMA_OWNER; предназначен для первоначального развёртывания. Регистрация и остальные процедуры не повышают роль пользователя.

Регистрация, создание первого администратора, вход и выход — отдельные **автономные транзакционные конечные точки**, выполняющие собственный COMMIT. Это сохраняет счётчик неудачных входов и отзыв сессий даже при ROLLBACK внешнего клиента. Их нельзя вызывать из транзакции, удерживающей незавершённые изменения соответствующих пользователей/сессий: возможна взаимная блокировка. Перед тестовым входом fixture пользователей необходимо зафиксировать либо создать через register_user.

Вход выполняет дорогую проверку пароля до захвата строки пользователя; после блокировки повторно проверяет изменившийся хеш и актуальные роль/статус. Неуспех атомарно увеличивает failed_unlock_attempts максимум до 5, пятая ошибка устанавливает Blocked. Успех сбрасывает счётчик. Неверный логин, пароль и закрытая учётная запись дают одинаковую ошибку -20301; для отсутствующего пользователя выполняется фиктивная PBKDF2 с рабочими 600000 итерациями. Это снижает различия по времени, но не является обещанием идентичной длительности исполнения. Отдельные лимиты запросов и защита от массовой блокировки аккаунтов требуются на сетевом входе.

Ошибки БД не скрываются: изменения автономного вызова откатываются и исходная ошибка передаётся выше; счётчик/аудит уже зафиксированного неудачного входа не отменяется последующим ROLLBACK. В аудит пишется субъект (для неизвестного логина NULL), действие и SESSION_USER БД, без введённого логина, пароля, токена или их хешей. Проверки регистрации используют -20300, отсутствие аутентификации -20301, отсутствие административного права -20302; политика пароля сохраняет -20201 из PKG_PASSWORD.

Смена пароля, восстановление/разблокировка, назначение консультанта и очистка истёкших сессий должны вызываться отдельными административными процедурами; данный файл их не добавляет. Удаление таблиц, изменение существующих полей и прямой доступ приложения к auth_sessions не требуются.
