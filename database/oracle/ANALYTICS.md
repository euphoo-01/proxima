# Серверные рыночные данные и аналитика

`PKG_MARKET` (`sql/28_market.sql`) принимает реальные данные адаптеров; сам не вызывает HTTP и не создаёт котировки. `PKG_ANALYTICS` (`sql/29_analytics.sql`) читает историю и выполняет расчёты. Пакеты не меняют ER. Предварительные требования: основная схема и `PKG_AUTH`; доступ приложения — только `EXECUTE`. Настройку grants выполняет общий скрипт развёртывания.

## PKG_MARKET

Все методы принимают `p_token VARCHAR2` первым параметром. Только действующий администратор записывает инструменты, котировки и валютные курсы. История котировок общедоступного справочника читается любой действующей прикладной ролью. Запись и безопасный аудит находятся в транзакции вызывающего кода: `COMMIT` отсутствует, ошибка откатывает только свою процедуру.

| Метод после p_token | Контракт |
|---|---|
| `save_instrument(p_id IN OUT RAW, p_ticker VARCHAR2, p_name VARCHAR2, p_type VARCHAR2, p_currency VARCHAR2, p_exchange VARCHAR2, p_isin VARCHAR2)` | NULL ID создаёт, непустой ID изменяет существующий инструмент. Тип: Stock, ETF, Cryptocurrency; валюта из справочника. Валюта созданного инструмента неизменяема. ID определяет идентичность: автоматического объединения по тикеру нет, поскольку тикер сам по себе не уникален и существующая ER не содержит natural-key ограничения биржи/тикера. |
| `put_price(p_instrument_id RAW, p_price_time TIMESTAMP WITH TIME ZONE, p_price NUMBER, p_currency VARCHAR2, p_source VARCHAR2)` | Положительная цена в валюте инструмента, непустой источник, время не из будущего. Upsert по ID инструмента, UTC-моменту и источнику. Повтор источника исправляет прежнее значение, разные источники сохраняются независимо. |
| `put_exchange_rate(p_rate_date DATE, p_from_currency VARCHAR2, p_to_currency VARCHAR2, p_rate NUMBER, p_source VARCHAR2)` | Положительный курс **за одну единицу исходной валюты**, обе валюты из справочника, источник обязателен. Дата приводится к TRUNC; будущая UTC-дата запрещена. Идентичная пара имеет курс строго 1. Upsert по дате, валютной паре, источнику. |
| `get_price_history(p_instrument_id RAW, p_from_time TIMESTAMP WITH TIME ZONE, p_to_time TIMESTAMP WITH TIME ZONE, p_result OUT SYS_REFCURSOR)` | Включительные границы; колонки `instrument_id` (HEX), `price_time_utc`, `price`, `currency`, `source`. Все источники сохраняются видимыми, их строки нельзя суммировать как независимые торговые дни. |

`quote_cache` содержит последнюю по времени котировку. При равном моменте выбирается лексикографически первый источник с бинарной сортировкой; старый backfill не откатывает кэш назад. При исправлении исторической записи кэш восстанавливается из всей истории инструмента. Записи цен сериализуются блокировкой инструмента. Различающиеся цены источников не усредняются и не объявляются одинаковыми; правило выбора детерминированное, а не рейтинг качества поставщиков.

Ошибки параметров: `-20700`, отсутствующий инструмент: `-20701`; ошибки авторизации — контракт `PKG_AUTH`.

## PKG_ANALYTICS.snapshot_as_of

`snapshot_as_of(p_token VARCHAR2, p_portfolio_id RAW, p_as_of TIMESTAMP WITH TIME ZONE, p_result OUT SYS_REFCURSOR)` разрешён инвестору/консультанту только для своего активного портфеля; администратору не даётся обход прав. Момент обязателен и не должен быть будущим. Вычисления используют операции до него включительно, а не текущие агрегаты `assets.quantity`.

Для целостного отчёта при одновременной записи вызывающая сторона **до первого обращения к данным** начинает `SET TRANSACTION READ ONLY` либо транзакцию с `ISOLATION LEVEL SERIALIZABLE`. Пакет сам не меняет транзакционный режим и не делает скрытый COMMIT. Без этой границы действует стандартный READ COMMITTED с согласованностью отдельного SQL-оператора, а не всех запросов отчёта вместе. После завершения чтения вызывающая сторона заканчивает свою транзакцию. Интеграционные фикстуры проверяют чтение своих ещё не зафиксированных записей и потому не включают read-only режим внутри уже начатой транзакции.

- Количество: сумма Buy минус Sell. Отрицательная позиция — ошибка целостности истории.
- Деньги каждой валюты: Deposit + Sell − Buy − Withdrawal − комиссии − удержанные налоги.
- Стоимость позиции: количество × последняя известная цена не позднее момента оценки × курс на UTC-дату оценки. При равном времени — бинарно первый источник, как у кэша.
- Общая стоимость: деньги + стоимость инструментов в базовой валюте.
- Внешний поток: Deposit − Withdrawal **до комиссий**, каждый поток пересчитывается по курсу на свою UTC-дату. Поэтому комиссии уменьшают прибыль, не притворяясь меньшей внесённой суммой.
- Денежный P&L: стоимость − суммарный внешний поток. Включает результат изменения валютных курсов относительно исторических пополнений.
- Простой ROI: `100 × P&L / net_external_flows`, только если знаменатель положителен. Это явно именованный простой ROI, не TWR, IRR или годовая доходность.

Курсы: сначала идентичная пара 1; затем самая свежая дата не позже требуемой среди прямой и обратной пары, при равной дате прямая предпочтительна, затем бинарно первый источник. Если такой пары нет — две доступные ветви через BYN. Каждая ветвь берёт последний курс на свою дату; их даты и источники включаются в результат. Будущие курсы не используются. Курсы уже должны быть нормализованы на одну единицу валюты; номинал НБРБ учитывает адаптер до записи.

Курсор — одна строка: `base_currency`, `as_of_time`, `total_value`, `cash_value`, `asset_value`, `net_external_flows`, `pnl`, `roi_percent`, `missing_count`, `issues_json CLOB`, `valuation_json CLOB`.

`issues_json` содержит тип проблемы (`price`, `cash_fx`, `asset_fx`, `external_flow_fx`), ID затронутого ресурса и валюту. `missing_count` — количество проблем, не число уникальных валют. При неполной текущей оценке стоимость и её части NULL. Если отсутствует лишь исторический курс внешнего потока, стоимость доступна, но внешний поток/P&L/ROI NULL. Нули вместо отсутствующих цен и курсов не подставляются. `valuation_json` содержит исходные суммы и валюты, использованные курсы с датами/источниками и цену/время/источник для позиций. Это свидетельства расчёта, не второе хранилище позиций.

Данный этап поддерживает только Deposit, Withdrawal, Buy, Sell, как реализованный ledger. При других типах истории расчёт явно отклоняется; отсутствующие алгоритмы не маскируются произвольным знаком суммы. Смешанная история не получает заведомо неверный итог.

## PKG_ANALYTICS.instrument_risk

`instrument_risk(p_token VARCHAR2, p_instrument_id RAW, p_from_date DATE, p_to_date DATE, p_source VARCHAR2, p_periods_per_year NUMBER, p_risk_free_percent NUMBER, p_result OUT SYS_REFCURSOR)` читает общедоступные рыночные данные после проверки токена. Источник указывается явно: разные providers не смешиваются. Период — включительные UTC-даты, текущий незавершённый UTC-день исключён. Для каждой даты выбирается последняя записанная цена. Адаптер должен загрузить завершённые дневные закрытия выбранного feed: существующая таблица не позволяет доказать тип бара по одному значению цены.

`R[t] = close[t] / close[t−1] − 1`

`volatility = STDDEV_SAMP(R) × sqrt(periods_per_year)`

`rf_daily = (1 + risk_free_percent / 100)^(1 / periods_per_year) − 1`

`Sharpe = (AVG(R) − rf_daily) / STDDEV_SAMP(R) × sqrt(periods_per_year)`

`MDD = MAX(1 − close[t] / MAX(close[0..t]))`

Частота задаётся явно: 252 или 365, без скрытого выбора для смешанного портфеля. Единственный источник безрисковой ставки — `user_settings` текущего пользователя, ставка хранится в годовых процентах. `p_risk_free_percent=NULL` означает использовать сохранённую ставку; ненулевой параметр не переопределяет её и обязан точно совпасть с ней, иначе ошибка. При отсутствии настройки или несовпадении её валюты с валютой инструмента Sharpe NULL с явным статусом, остальные доступные метрики рассчитываются. Доходности обычные, не логарифмические; волатильность и MDD возвращаются долями, Sharpe безразмерен.

Курсор: `price_count`, `return_count`, `first_day`, `last_day`, `source`, `periods_per_year`, `risk_free_rate_percent`, `annualized_volatility`, `sharpe_ratio`, `maximum_drawdown`, `max_calendar_gap_days`, `calculation_status`, `risk_free_status` (`CONFIGURED`, `MISSING_RISK_FREE_RATE`, `RISK_FREE_CURRENCY_MISMATCH`). Для менее двух доходностей метрики NULL и статус `INSUFFICIENT_DATA`. При нулевой волатильности Sharpe NULL, а волатильность может быть честным нулём. При достаточном числе значений статус `OBSERVED_DAILY_SERIES` означает расчёт по наблюдениям, а не обещание полного торгового календаря: `max_calendar_gap_days` раскрывает разрывы. Пропущенные дни не заполняются вымышленными ценами; годовой пересчёт корректен при полной дневной последовательности выбранного календаря. До внедрения торгового календаря нельзя представлять эту метрику как проверенную годовую оценку при пропусках торговых дней.

Ошибки аналитики: `-20720` — роль, `-20721` — параметры/неподдерживаемая история, `-20722` — недоступный портфель. Авторизация не возвращает чужие данные.

## Границы этапа

TWR портфеля, риск смешанного портфеля, налоговые правила РБ, обработка корпоративных действий и ML не считаются реализованными этими пакетами. TWR требует согласованного разделения потоков и оценок на границах подпериодов; деление конечной стоимости на пополнения его не заменяет. VWAP не вычисляется из `asset_prices.price`: в текущей модели нет объёмов торгов. Не создаются поля или ложные нулевые показатели ради видимости полноты.

`sql/103_analytics_tests.sql` содержит изолированные синтетические фикстуры для проверки формул и прав; они не являются наполнением рыночной истории приложения. Пока скрипт не выполнен на Oracle, он считается подготовленным, а не пройденным.
