# Уточнение требований к переходу на Oracle

Документ фиксирует решения интервью от 18 ноября 2026 года. Исходное задание — `spec/assignment.docx`, проектная модель — `spec/er-model.drawio`, сценарии — `spec/use-cases.md`. Эти исходные материалы сохранены в репозитории для воспроизводимой работы агентов; исторический контекст — `spec/previous-context.md`.

## Принятые решения

- Проектирование ведётся от универсальной абстракции к конкретной реализации. Используются паттерны адаптера и репозитория; существующие подходящие контракты переиспользуются без дублирования. Контракты определяются потребностями приложения и не зависят от API конкретного поставщика.
- Разработка продолжается в существующем репозитории `euphoo-01/proxima`, без отдельной демонстрационной версии приложения. Новые функции интегрируются в обычные экраны и стандартный запуск. После каждой изменившейся итерации создаётся коммит; публикация в тот же GitHub-репозиторий разрешена. README отражает курсовую по БД пятого семестра и фактическую готовность перехода.
- Приоритет ближайших итераций — проверяемая БД и видимые функции основного приложения для демонстрации. Контекст агентов и повторные проверки ограничиваются текущим срезом; расход квоты контролируется, числовая оценка оставшегося лимита не означает гарантированного объёма реализации.
- Получение котировок имеет общий контракт и отдельные адаптеры для каждого источника. Особенности авторизации, внешних форматов, лимитов и ошибок поставщика остаются внутри адаптера. Реализации репозиториев Oracle обращаются к данным через серверный API процедур.
- Сохраняются Avalonia UI и стилистика приложения. Цена единицы, количество и комиссия отображаются отдельно; комиссия не маскируется изменением исходной цены.
- Бизнес-правила, финансовые расчёты, проверка доступа и изменения данных выполняются в Oracle. C# отвечает за представление, навигацию, интеграции и передачу файлов.
- Создаётся новая БД в Docker Compose с тестовыми данными по требованиям курсового; миграция старых данных не требуется.
- Изменение ER допускается только при острой необходимости после объяснения причин, альтернатив и получения отдельного разрешения пользователя.
- Операции являются источником истины для количества и себестоимости позиции. Операции разрешено редактировать, в том числе после последующих продаж, если исправленная история остаётся корректной.
- Короткие позиции запрещены. Создание, редактирование и импорт должны исключать отрицательный остаток на любом шаге истории. Проверка и запись атомарны и защищены от конфликтующих одновременных изменений.
- Учитываются денежные остатки по валютам, пополнения, выводы и денежные последствия операций. Быстрая работа обязательна; конкретные показатели производительности ещё не согласованы и не измерены.
- Для реализованной прибыли принят FIFO. Налоговая юрисдикция — РБ; допустимость метода и налоговое признание расходов необходимо проверить по первичным источникам до реализации налогового алгоритма.
- Комиссия покупки включается в себестоимость, комиссия продажи уменьшает выручку для учётной прибыли. Налоговые правила проверяются отдельно.
- Портфель имеет базовую валюту оценки, исходные валюты и суммы операций сохраняются. Для исторических расчётов используются исторические курсы; налоги рассчитываются в BYN.
- При отсутствии курса на дату используется последний доступный курс на эту дату или раньше; дата фактически использованного курса отображается. При полном отсутствии подходящей истории расчёт недоступен с объяснением.
- Покупка требует достаточного денежного остатка в соответствующей валюте с учётом комиссии. При исправлении истории проверяется достаточность остатков на каждом шаге. Предусматривается ввод начальных остатков денег и инструментов.
- Обмен валют оформляется явной операцией с фактическими суммами списания, зачисления и комиссией. Оценочная конвертация не меняет денежные остатки; автоматического обмена при покупке нет.
- Первая реализация охватывает акции, ETF и криптовалюты. Облигации в неё не входят. Налоговая применимость проверяется отдельно для каждой категории.
- При регистрации назначается роль инвестора. Консультанта назначает администратор; первый администратор создаётся при первоначальном развёртывании. Самостоятельное повышение прав запрещено.
- При любой работе с интерфейсом обязательно применяется навык `impeccable` с сохранением стилистики Proxima и адаптацией рекомендаций к Avalonia UI.
- Импорт проверяется целиком и сохраняется атомарно; ошибочный пакет не записывается частично.
- XML отменён пользователем. Импорт и экспорт используют CSV по листу задания, обработка выполняется средствами Oracle; приложение передаёт содержимое и сохраняет полученный файл. Оба направления используют согласованную семантику данных и серверные проверки.
- При недостатке рыночных данных соответствующий расчёт недоступен с объяснением. Произвольные подстановки доходности запрещены. Пользователи и операции набора наполнения вымышленные, история котировок реальная; происхождение данных отражается в технической документации. По явному решению пользователя в интерфейсе и названиях портфелей слово «тестовый» и соответствующие пометки не используются.
- Для аналитики приняты денежная прибыль и TWR, исключающий влияние внешних денежных потоков. Формула обязательного ROI согласуется отдельно. Перечень показателей должен быть явно виден в интерфейсе; вариант общего выбора периода ещё уточняется.
- Показатели риска рассчитываются по ежедневной истории выбранного периода, по умолчанию за последний год, с учётом различий фондового и криптовалютного календарей.
- Горизонт ML-прогноза — пять торговых дней для акций и ETF, пять календарных дней для криптовалют. Качество проверяется на отложенном временном интервале; показываются дата обучения и ошибки прогноза.
- Обучение моделей запускает администратор вручную. Пользовательские страницы читают сохранённые результаты и не запускают обучение при открытии.
- Повтор уже принятого файла блокируется, похожие операции из разных файлов отмечаются как возможные дубликаты. Требуется удобный групповой разбор дубликатов; конкретный сценарий выбора и удаления ещё согласуется.
- Основные кандидаты источников одобрены: Alpaca для акций США и ETF, Binance для криптовалют. Перед интеграцией проверяется фактическая доступность аккаунта и feed Alpaca; её доступность из Беларуси не считается подтверждённой. Исследование и ограничения: `market-data-research.md`.
- Для учебного проекта допустима задержка котировок акций до 15 минут; источник и время цены показываются пользователю.
- Общий выбор периода аналитики одобрен: месяц, квартал, год, весь период, произвольные даты. Он должен быть компактно интегрирован без перегрузки страницы; при необходимости значение по умолчанию выносится в настройки. Окончательное размещение определяется при работе с UI через `impeccable`.
- Разбор дубликатов групповой: сравнение похожих операций, выбор сохраняемой операции, применение к нескольким группам и предварительный просмотр результата. Автоматического удаления нет; изменения атомарны после проверки остатков. Подтверждённые отдельные сделки больше не помечаются как дубликаты.
- Начальные вложения вводятся либо реальными отдельными покупками, либо начальным остатком с датой, количеством, валютой и общей себестоимостью с комиссиями. Общий остаток явно помечается как ограниченная история и не выдаётся за восстановленные покупки для точного FIFO. При неизвестной себестоимости она не заменяется нулём: соответствующие прибыль и налог отмечаются как неполные.
- Создание, исправление и удаление операций отражаются в доступном администратору журнале: субъект, время и содержание изменения. Исключение операции из расчётов не уничтожает след действия. Исправление и пересчёт атомарны.
- Хранятся время и порядок операций внутри дня. Неоднозначный порядок пользователь может исправить; автоматическая перестановка не должна быть молчаливой. Конкретный способ подтверждения определяется при проектировании импорта.
- Средняя цена собственных покупок и рыночный VWAP — разные показатели. Рыночный VWAP при недостатке подходящих данных не отображается.
- Безрисковая ставка — явный годовой параметр с валютой, хранится централизованно, применяется Oracle и доступна в настройках аналитики.
- Прогноз достижения финансовой цели — формульный сценарный расчёт по начальному капиталу, целевой сумме, регулярным пополнениям и явно заданной ожидаемой доходности. Предположения видны пользователю; скрытые фиксированные доходности и обещания достижения цели исключены.
- ML остаётся в ранее согласованных границах: прогноз цены инструмента и кластеризация активов. Отдельная ML-модель достижения цели не создаётся; пятидневный прогноз цены не экстраполируется на многолетний срок цели.
- Блокировка пользователя лишает доступа также открытые сессии: действительность сессии проверяется при каждом вызове прикладной процедуры. Приложение сообщает о блокировке и возвращает на экран входа.
- Сформированный отчёт фиксирует результат на момент формирования, период и параметры расчёта. Исправление операций влияет на новые расчёты и не переписывает ранее сформированный документ; отчёт не является отдельным редактируемым источником данных.
- Набор наполнения содержит вымышленных пользователей и операции, реальные сохранённые котировки. Для проверки производительности создаётся объём минимум 100 000 строк. Сохранённые данные доступны для аналитики без повторного обращения к внешнему API.
- Портфель с операциями архивируется вместо обычного физического удаления. Администратору доступны в интерфейсе просмотр архивных портфелей, восстановление и окончательное удаление с подтверждением. Удаление не должно уничтожать журнал действий. Пустой портфель можно удалить.
- При неполных данных для налогов доступная сумма показывается с заметной пометкой «Расчёт неполный», числом проблем и действием «Что исправить» со списком затронутых операций. После исправления исходных данных сумма пересчитывается. Неполный результат не называется окончательным и не блокирует остальную работу пользователя.
- Статус неполного налогового расчёта и число проблем компактно располагаются рядом с суммой в существующем стиле. Список проблем и переходы к исправлению раскрываются по действию пользователя; постоянный список не перегружает страницу. Решение проверяется через `impeccable`.

## Следующие уточнения

- Источники курсов и котировок.
- Детальная семантика начальных остатков и остальных операций, точности и порядок операций с одинаковым временем.
- Методики доходности и риска, параметры ML и критерии качества.
- Техническая реализация сессий и первоначального развёртывания, проверка возможностей целевой Oracle и прав внешних API.

Согласованные требования переведены в вертикальные задачи `implementation/backlog.json`; пользователь разрешил работу и публикацию в существующем репозитории. Реализация идёт поэтапно в основном приложении. Технические и методические вопросы выше проверяются до соответствующего среза, а необходимые продуктовые решения возвращаются пользователю.
