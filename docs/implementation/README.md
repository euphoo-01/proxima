План работ по `to-issues` из workflow Matt Pocock. Источник требований — [oracle-requirements.md](../oracle-requirements.md), архитектурных решений — [ADR](../adr/). Отдельный PRD с повторением тех же требований не нужен. [backlog.json](backlog.json) — единственный редактируемый источник задач: ID, зависимости, сценарии, критерии приёмки и команды проверки. Работа ведётся в существующем GitHub-репозитории `euphoo-01/proxima`. До публикации отдельных Issues канонический backlog хранится в этом репозитории.

## Запуск

Нужны Linux/macOS, Python 3, Git, установленный и авторизованный Codex CLI. Модель и провайдер берутся из его текущей конфигурации. Docker, .NET, SQL-клиент и внешние ключи потребуются при исполнении задач; отсутствие доступа должно останавливать задачу, а не заменяться моками. Инструкция CLI: [официальный non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode).

Из корня `proxima_v1`:

```bash
bash scripts/ralph.sh plan
python3 -m unittest discover -s scripts/ralph -p 'test_*.py' -v
```

Эти команды не запускают AI и не меняют приложение. `plan` валидирует граф и выводит порядок, зависимости и сценарии. Сначала согласуйте гранулярность и зависимости задач. Поле `approved` в JSON обозначает согласование плана; после согласования установите его в `true`.

Если модель глобального профиля CLI недоступна текущему способу авторизации, передайте `--model <доступная-модель>` в `run`. Это переопределение только текущего запуска; глобальные настройки и ключи не меняются. Доступность определяется фактическим ответом аккаунта, а не одним наличием модели в локальном кеше. Первая проба в этой среде остановлена до работы: сервер отклонил `gpt-6.1-sol` для ChatGPT sign-in. Не запускайте повторяющиеся попытки с заведомо недоступной моделью.

Перед первым запуском сохраните текущее дерево в Git. Скрипт требует чистого дерева. Коммиты после каждой изменившейся итерации создаёт runner: завершённый срез отмечается complete, незавершённая попытка — wip. Предварительная оценка исходной сборки входит в S01.

После согласования и сохранения файлов:

```bash
bash scripts/ralph.sh approve
bash scripts/ralph.sh run --max-iterations 1 --timeout 1800 --push
bash scripts/ralph.sh status
```

После наблюдения за первой итерацией можно запускать ограниченную серию:

```bash
bash scripts/ralph.sh run --max-iterations 5 --timeout 1800 --push
```

Каждая итерация — новый процесс исполнителя, затем команды проверки и новый процесс проверяющего в read-only sandbox. В этом варианте агенты работают последовательно в одном дереве: независимые ветки графа не означают, что безопасно одновременно редактировать общие файлы. Блокировка исключает два экземпляра этого runner в одном репозитории; сторонние процессы она не блокирует. Не редактируйте дерево и не делайте коммиты во время серии. Коммиты автоматические после каждой изменившейся итерации; `--push` отправляет их обычным push в origin текущей ветки. Автоматического merge и force-push нет.

`--max-iterations` ограничивает попытки задач, не число AI-вызовов: успешная попытка вызывает исполнителя и проверяющего. `--timeout` ограничивает каждый отдельный процесс, а не всю серию; один срез может занять больше времени. Оплата и ограничения аккаунта Codex сохраняются. Проверки выполняются без shell-интерполяции, workspace-write для исполнителя, read-only для проверяющего; обход sandbox/approvals не используется. Логи могут содержать технические данные: `.ralph/` исключён из Git.

## Состояние и остановки

- `.ralph/state.json` хранит завершённые задачи и обратную связь. Каждая попытка имеет отдельные JSON-ответы и логи. Состояние не дублирует требования.
- `completed`: исполнитель заявил завершение, все внешние команды прошли, независимый проверяющий подтвердил критерии. Сборка не заменяет реальный SQL-тест или визуальную проверку; если они недоступны, задача не готова.
- `retry`: следующая итерация продолжает тот же срез с замечаниями; зависимые задания не запускаются.
- `needs_user`: цикл останавливается. Примеры: изменение ER, ключ Alpaca, права Docker, недоказанная налоговая методика. Решение нельзя получить истечением времени.
- После решения внешней проблемы: `bash scripts/ralph.sh unblock S01`, затем новый `run`. Если изменились требования, план или скрипты, снова нужны согласование и `approve`. Изменённый план не должен наследовать завершение старых задач без пересмотра.
- Если после остановки вручную исправляли файлы или делали коммит, сначала осмотрите diff, затем выполните `bash scripts/ralph.sh checkpoint`: эта команда явно принимает текущее дерево как точку продолжения. Она не одобряет изменения требований. При изменении защищённого плана после начала работы требуется сохранить старую `.ralph/` отдельно и начать новое состояние с пересмотром задач; `approve` не переносит прежние статусы автоматически.
- Ошибка CLI, некорректный JSON, timeout или прерывание прекращают процесс и сохраняют уже записанный прогресс; текущие изменения остаются для осмотра, автоматического отката нет. `Ctrl+C` завершает группу текущего дочернего процесса.
- Коды выхода: `0` — план/статус/все задачи завершены; `2` — нужна проверка пользователя или ошибка; `3` — лимит попыток, есть незавершённые задачи. Сам код `0` от AI никогда не равен готовности среза.

Это автоматизация обратной связи, а не доказательство корректности. Человеческая приёмка финансовых правил и визуального результата остаётся необходимой. Начинать следует с одной итерации, оценивая расход квоты и реальный результат.
