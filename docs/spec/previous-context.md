# Контекст проекта Proxima — курсовая работа по базам данных (Oracle)

> **Назначение документа.** Перенос подробного контекста из беседы ChatGPT (27–28 октября 2026 года) в новый чат. Это **структурированная передача содержания и решений**, а не буквальная пословная выгрузка всех сообщений. Сохраняются важные требования, согласованные выборы, аргументация, структура ER v4, полный перечень связей, история версий, требования к Use Case и следующий план действий.
>
> **Ключевой ориентир:** самая актуальная версия ER — `Proxima_Oracle_ER_v4_FullFields_FieldConnections.drawio`. Модель **проектная**, а не признак, что Oracle БД и процедуры уже реализованы. Сведения в секциях 6–7 дополнительно извлечены из XML этой версии.

## 1. Суть проекта и решения пользователя

- Студент выполняет курсовую работу по дисциплине «Базы данных» в БГТУ (3 курс, группа 7).
- Новая официальная тема: **«Разработка базы данных системы учета и анализа финансовых активов с применением средств продвинутой аналитики Oracle»**.
- В качестве основы берётся прошлогодний курсовой по ООП — настольное приложение **Proxima** для учёта и анализа финансовых активов, ранее основанное на PostgreSQL, .NET/C#, Avalonia UI, MVVM и EF Core.
- В новой работе сохраняется **Avalonia UI** и существующий внешний вид приложения; существенно меняется слой доступа к данным. Основные операции и расчёты переносятся в Oracle через **PL/SQL-пакеты, процедуры и функции**.
- СУБД выбрана **Oracle Database 23ai / 26ai** (точная установленная сборка ещё не подтверждена).
- Три роли: **администратор**, **частный инвестор**, **финансовый консультант**. Для администратора нужно расширить UI полноценными экранами в существующем стиле Proxima.
- **ОКОНЧАТЕЛЬНЫЙ ВЫБОР ML:** **ML-1 — прогнозирование стоимости/цены финансового инструмента** и **ML-3 — кластеризация финансовых активов**. **ML-2 — поиск аномальных транзакций — НЕ ИСПОЛЬЗОВАТЬ.** Ранее ассистент ошибочно называл ML-2 выбранной задачей; пользователь это поправил.
- В ближайшем приоритете — подготовить **ER-диаграмму и UML Use Case** к сдаче; затем реализовать Oracle и соответствующую адаптацию интерфейса.

## 4. Требования преподавателя к диаграммам (из DOCX)

**Нужно различать:** актуальный курсовой — по БД; файл с требованиями к диаграммам также содержит список схем для смежных курсовых. Первоначально пользователю надо сдать **Use Case и логическую схему БД (ER)**, остальные диаграммы — по необходимости согласно указаниям преподавателя.

### ER / логическая схема БД

- Чёрно-белый стиль чертежа.
- Показать таблицы, атрибуты, обозначения `PK` и `FK` и кратности связей в нотации, аналогичной **Crow's Foot**.
- Если атрибутов очень много, **формально допускается** показывать только существенные, однако пользователь **явно выбрал показывать все 148 предусмотренных полей**.
- Допускается физическая модель с типами данных, ограничениями и т. п. В ER v4 типы Oracle **ещё не прописаны во всех столбцах**, это пока подробная логическая модель.
- Связи — **сплошные** линии с корректными маркерами кратности; соединение должно физически выходить **сбоку из строки PK** и приходить **сбоку в строку FK**.
- **Никаких текстовых подписей поверх связей** вроде `from_currency → currencies.code`: связь определяется её концами.
- **Не писать `[NULL]` или `<NULL>` в названиях полей.** Необязательность фиксируется на уровне правил/кратности и впоследствии DDL-ограничений.
- **Одна логическая связь PK–FK = отдельная линия.** Даже если `currencies.code` ссылается одновременно из `exchange_rates.from_currency` и `exchange_rates.to_currency`, необходимо провести **две независимые линии**, а не одну ветвящуюся.
- Избегать пересечений линий; если неизбежно — в draw.io включать «Перемычка линий» (`jumpStyle`).
- Важно: это **требования конкретного преподавателя**, а не утверждение, что все такие особенности буквально и универсально предписаны ГОСТом.

### UML Use Case

- Чёрно-белый чертёж, большой **прямоугольник границы системы**, название сверху.
- Варианты использования — **одинаковые овалы**; один вариант = одна функция.
- Названия через **существительные/отглагольные существительные**: «Добавление операции», не «Добавить операцию».
- Обязательно показать зависимости `<<Включить>>` / `<<Расширить>>` (обычная UML-терминология `include` / `extend`).
- Линии связей актор–вариант: прямые, без скруглений и углов; это особенно важно для Use Case (не путать с ортогональными связями ER).
- **Никакой автогенерации Use Case**; собирать **вручную в draw.io / Visio**.

## 5. Предыдущая архитектура Proxima и переход к Oracle

### Существующий проект по ООП

- Приложение `Proxima.App`: Avalonia UI 11.3, XAML Views, MVVM ViewModels, навигация, дизайн-система, дашборд и отчёты.
- `Proxima.Core`: доменные сущности и бизнес-логика (`User`, `Portfolio`, `Asset`, `Transaction`, `Goal`, `UserNotification` и др.), сервисы и интерфейсы.
- `Proxima.Infrastructure`: PostgreSQL, `ProximaDbContext`, EF Core, миграции, репозитории, провайдер котировок Twelve Data, курсы НБРБ / Беларусбанк, импорт CSV, PDF-экспорт.
- `Proxima.Tests`: тесты бизнес-логики, архитектуры, хранения и отчётов.
- В предыдущей пояснительной записке были модули входа, портфелей, активов, транзакций, CSV-импорта, котировок, финансовой аналитики, целей, налогового расчёта, PDF, уведомлений, пользовательских настроек.
- Предыдущая реализация использовала PBKDF2-SHA256 credential (соль, итерации и хеш), логин/роль и счётчик неудачных попыток. Не хранить открытые пароли.
- В старой записке `portfolios.client_label` ошибочно/непоследовательно описывался как boolean, тогда как в коде (по предшествующему анализу) это строка. При переносе нужно сверять реальный исходник.
- `transactions.asset_id` может быть необязательным для пополнений и выводов без актива.
- Старый `quote_cache.asset_id` не имел полноценного FK в конфигурации EF Core; в новой модели он заменяется `instrument_id`.

### Предлагаемый переход

`Avalonia View → ViewModel → C# сервис доступа к Oracle / ODP.NET → PL/SQL пакет/процедура → таблицы Oracle → результат (например SYS_REFCURSOR / DTO) → ViewModel`.

- **Сохранить существующий UI и стиль**; переписать слой сохранения и расчётов под процедурный интерфейс Oracle.
- Oracle выполняет бизнес-правила и финансовые вычисления; C# отвечает за UI, локальные диалоги, чтение/сохранение файлов, представление полученных результатов.
- Для PDF Oracle подготавливает отчётные данные, а существующий C# PDF-генератор может оформлять итоговый документ.
- Входящие CSV читаются в приложении/адаптере, проверка, импорт и фиксация данных происходят через Oracle-процедуры.
- Конкретные версии `ODP.NET` и поддержка .NET 10 должны быть проверены на реально установленной Oracle-сборке при реализации.
- Для безопасности следует отделить **роли Proxima** (`ADMIN`, `PRIVATE_INVESTOR`, `FINANCIAL_CONSULTANT` или согласованные аналоги) от **пользователей/привилегий Oracle** и обеспечить проверку полномочий в серверном API.

### Почему структура разделена именно так

1. `instruments` описывает **сам финансовый инструмент** (например, акция NVDA), а `assets` — **позицию этого инструмента в конкретном портфеле**. Это предотвращает дублирование описания инструмента и истории рыночных цен между портфелями.
2. `transactions` — **история первичных финансовых событий**; остатки, средняя цена и доходность выводятся из неё. Поля `assets.quantity`, `average_buy_price`, `current_price` оставлены как вычисляемое/кэшируемое состояние; их синхронизацию должны обеспечивать Oracle-процедуры.
3. `asset_prices` — единая история котировок **по `instruments`**, нужная как для графиков, так и для ML-прогнозирования и тестирования производительности.
4. `quote_cache` — последняя известная котировка инструмента; `portfolio_snapshots` — исторические значения портфеля, чтобы не пересчитывать длинную историю при каждом открытии дашборда.
5. `currencies` — центральный справочник валют. У `exchange_rates` есть **две отдельные FK** на `currencies.code` — исходная и целевая валюты. Курс **не** связан непосредственно с каждой транзакцией: он подбирается по паре валют и дате в расчёте.
6. `asset_tags` реализует логическое M:N между позициями и тегами. `assets` одновременно реализует логическое M:N между портфелями и финансовыми инструментами.
7. `import_batches` и `import_rows` обеспечивают предварительную проверку CSV, отслеживание ошибок и воспроизводимость импорта.
8. ML разделён на метаданные модели (`ml_models`), конкретные запуски обучения (`ml_training_runs`) и результаты применения (`ml_results`). Сам обученный объект живёт в Oracle, а не записывается целиком в эти таблицы.

### Как проверять Crow's Foot

- На **стороне дочерней таблицы (FK)** для большинства связей — `0..N` («лапка с кружочком»), потому что у одного родителя может не быть дочерних записей или их может быть много.
- На **стороне родителя (PK)** для обязательного FK — `1` (дочерняя запись обязана ссылаться на одного родителя).
- Для необязательного FK на стороне PK отмечено `0..1`, как в связях `audit_log.user_id`, `transactions.asset_id`, `transactions.import_batch_id`, `ml_training_runs.instrument_id`.
- Для `users.id → user_settings.owner_user_id` и `instruments.id → quote_cache.instrument_id` со стороны дочерних записей — **`0..1`**, то есть отношение один-к-нулю-или-одному. Требуется `PRIMARY KEY` на user_settings FK и `UNIQUE(instrument_id)` на quote_cache.
- Нельзя объединять две PK→FK связи в одну ветвящуюся линию. Например, `currencies.code` в `exchange_rates.from_currency` и `exchange_rates.to_currency` — **два разных отношения**, даже если кратность одинакова.

### Планируемые ограничения целостности — ещё подлежат реализации

- `users.login`: `UNIQUE` и запрет пустых логинов; `role`, `account_status` — ограниченный набор допустимых значений.
- `quote_cache.instrument_id`: `UNIQUE` для обеспечения 1:0..1.
- `assets(portfolio_id,instrument_id)`: `UNIQUE` при бизнес-правиле «одна агрегированная позиция на инструмент в портфеле».
- `transactions(asset_id,portfolio_id) → assets(id,portfolio_id)`: составной FK, чтобы транзакция не ссылалась на актив другого портфеля; потребуется соответствующий уникальный ключ со стороны assets.
- `asset_prices(instrument_id,price_time_utc,source)`: уникальность по инструменту/моменту/источнику (проверить политику по интервалам и провайдерам).
- `exchange_rates(rate_date,from_currency,to_currency,source)`: уникальность; `rate > 0`.
- `portfolio_snapshots(portfolio_id,snapshot_date)`: уникальность снимка на дату.
- `tags(owner_user_id,name)`: уникальность тега внутри одного пользователя.
- `asset_tags(asset_id,tag_id)`: составной PK (в диаграмме уже оба поля отмечены PK/FK).
- `import_rows(batch_id,row_number)`: уникальная строка внутри партии импорта.
- `ml_training_runs.oracle_model_name`: проверка уникальности зарегистрированных Oracle-моделей.
- `ml_results`: ограничения согласованности `result_type`, `predicted_price`, `forecast_date`, `cluster_id`, `cluster_distance` (не путать прогноз цены с кластером; уточнить `NULL`/`CHECK`).
- `transactions.external_id`: защита от повторного импорта в рамках источника/брокера.
- Определить `NOT NULL`, `ON DELETE`, числовые точности, индексы, транзакционную согласованность агрегатов и политику временных зон.

### Обсуждавшиеся типы Oracle (проектные предложения, НЕ полный DDL)

- UUID — `RAW(16)`; строки — `VARCHAR2(n CHAR)`; деньги/цены — `NUMBER(20,8)` или другая подходящая заданной точности спецификация; проценты — `NUMBER(12,6)`; время события — `TIMESTAMP WITH TIME ZONE`; календарная дата — `DATE`; JSON-метаданные — `JSON` / совместимый вариант в конкретной версии Oracle.
- Для флагов ранее предложено `NUMBER(1)` + `CHECK`; реальная Oracle 23ai/26ai поддерживает дополнительные типы, поэтому окончательный выбор делать после уточнения версии и драйвера.
- Избегать логического противоречия: **само имя поля не содержит `[NULL]` или `<NULL>`**, но DDL-ограничения `NULL`/`NOT NULL` всё равно обязательны при реализации.

## 8. ML: окончательно ML-1 + ML-3, без поиска аномалий

### ML-1 — прогнозирование цены финансового инструмента

- Источник: `asset_prices`, привязанная к `instruments`.
- Задача: получить прогноз цены на будущие торговые дни, отобразить на странице детали актива. Можно применить **Oracle Machine Learning for SQL**, например **Exponential Smoothing** для временных рядов; конкретные параметры и применимость нужно проверить на целевой Oracle.
- Хранение: `ml_models` (задача `PRICE_FORECAST`, алгоритм), `ml_training_runs` (обучение для конкретного инструмента, метрики и период), `ml_results` (`result_type`, `instrument_id`, `forecast_date`, `predicted_price`).
- Качество: тестирование на отложенном **временном** интервале, например MAE/RMSE; не заявлять гарантию прибыли.

### ML-3 — кластеризация финансовых активов

- Источник: исторические котировки + рассчитанные по ним характеристики каждого инструмента — доходность, волатильность, максимальная просадка и потенциально другие финансовые факторы.
- Алгоритм-кандидат: **k-Means** Oracle Machine Learning for SQL.
- Обучение может относиться **к набору инструментов**, поэтому `ml_training_runs.instrument_id` допускает отсутствие конкретного инструмента.
- Хранение результата: `ml_results` со ссылкой на конкретный `instrument_id`, `result_type`, `cluster_id`, `cluster_distance`, `training_run_id`.
- В UI: группа/кластер актива и, при необходимости, список похожих инструментов/визуализация характеристик кластеров.

### Общие SQL-объекты Oracle для ML (пока идея, не создано)

- `V_ML_PRICE_SERIES` — подготовка временных рядов.
- `V_ML_ASSET_FEATURES` — вычисление/нормализация признаков для кластеризации.
- `PKG_ML.TRAIN_MODEL`, `PKG_ML.RUN_PREDICTION`, `PKG_ML.GET_RESULTS` — серверный API машинного обучения.
- Реализация предполагается через возможности `DBMS_DATA_MINING` / Oracle Machine Learning for SQL; наличие нужных опций, синтаксис и лицензирование проверять на конкретной СУБД.
- **Не включать** `V_ML_TRANSACTION_FEATURES`, One-Class SVM или обнаружение подозрительных транзакций в финальную концепцию: это было из ошибочно выбранной ML-2.

### Смысловые отношения `include` / `extend`

- `Импорт операций из CSV` **`<<Включить>>`** → `Проверка строк импорта` (проверка всегда при импорте).
- `Корректировка строк импорта` **`<<Расширить>>`** → `Импорт операций из CSV` (только при обнаружении ошибок; на расширении указать условие).
- `Просмотр сводки портфеля` **`<<Включить>>`** → `Расчёт финансовых показателей`, если сводка всегда требует расчёта.
- `Формирование PDF-отчёта` **`<<Включить>>`** → `Расчёт финансовых показателей`, **если** это обязательно для каждого PDF-отчёта; иначе пересмотреть.
- `Экспорт операций в CSV` **`<<Расширить>>`** → `Просмотр операций` — обсуждалось как вариант, но надо проверить, действительно ли экспорт является расширением сценария просмотра; нередко это самостоятельный Use Case.
- Не соединять каждую функцию с «Авторизация» через `include` — вход чаще является предусловием.
- Стрелка `include` направляется **к включаемому** варианту; `extend` — **от расширения к базовому**.
- Отдельный административный UI должен иметь свои сценарии в Use Case; в частности, администратор может просматривать метрики качества обученных моделей и запускать их переобучение.

## 12. История решений и уточнений по переписке

1. Пользователь загрузил старый курсовой по ООП, исходники, пояснительную записку, рисунки UML и лист нового задания. Цель — переиспользовать Proxima для курсовой по БД.
2. Подтверждено, что требуется **ER-диаграмма**, а не UML-диаграмма классов БД.
3. Пользователь выбрал **несколько ML-задач**, Oracle **23ai/26ai** и **сохранение Avalonia UI**.
4. После обсуждения окончательная ML-пара: **ML-1 (прогнозирование цены) и ML-3 (кластеризация)**. Ранее упомянутая ML-2 была ошибкой ассистента и исправлена.
5. Решено добавить **полноценные экран(ы) администратора**, оформленные в стиле существующего приложения.
6. Старый `.drawio` имеет шесть редактируемых страниц. ER сначала предполагалось расширить, Use Case — более радикально переделать вручную.

## 13. Важные неокончательные моменты и проверки перед сдачей

- **ER v4 не является окончательно утверждённым физическим Oracle DDL.** Она показывает структуру и связи; типы данных, ограничения и все зависимости нужно ещё формализовать и реализовать.
- Визуально проверить 32 линии в draw.io, особенно места пересечения, «перемычки», выравнивание и совпадение концов со строками ключей. Ранее были автоматические проверки XML, но это **не доказывает** отсутствие визуальных пересечений или полной соответствия ГОСТ/требованиям.
- В `quote_cache` физически обеспечить `UNIQUE(instrument_id)` для `1:0..1`.
- В `assets` решить, разрешены ли несколько позиций одного инструмента в одном портфеле. В зависимости от этого вводить или не вводить `UNIQUE(portfolio_id,instrument_id)`.
- В `transactions` сохранить согласованность `portfolio_id` и `asset_id` через составной внешний ключ/серверную проверку.
- Два логических M:N: `assets ↔ tags` через `asset_tags`; `portfolios ↔ instruments` через `assets`. На физической схеме не рисовать дополнительных прямых M:N линий.
- `exchange_rates` не связана напрямую с `transactions` — это **осознанное решение**, поскольку курс подбирается вычислением по валютной паре и дате. Но `exchange_rates.from_currency` и `to_currency` имеют отдельные FK на `currencies.code`.
- Продумать коды/составные ключи валют, систему базовых валют, торговые календари, нормализацию валютных котировок, качество финансовых данных для ML.
- Проектная таблица `ml_results` объединяет прогнозы и кластеризацию. Для каждого `result_type` нужно ограничить набор полей и условия уникальности; при усложнении можно разделить на две специализированные таблицы, но пока согласована единая модель.
- ML-обучение/вычисление средствами Oracle **ещё не реализовано**; не заявлять о работающем ML или проведённом тестировании.
- Проверить, как оформлять «смену роли пользователя»: административное право, которое нельзя давать обычному инвестору.
- Use Case ещё не собрана в новом виде. Собрать вручную по требованиям; не пытаться выдать старую Use Case за финальную.
- Системная безопасность: права Oracle, привилегии `EXECUTE` на API, SQL Injection, защита API-ключей и паролей, серверная проверка авторизации.
- Не утверждать автоматически доказанную 3НФ: схема **ориентирована на нормализацию**, но есть осознанная денормализация и расчётные поля, соответствие нормальным формам нужно оценивать по функциональным зависимостям.

## 14. Как защищать ER-структуру перед преподавателем

Основная идея защиты:

> При проектировании Proxima я разделил данные на самостоятельные сущности финансового учёта, рыночные данные, учёт пользователей, импорт и результаты интеллектуальной аналитики. Важное решение — разделение финансового инструмента (`instruments`) и позиции в конкретном портфеле (`assets`): один инструмент может встречаться в разных портфелях, но его котировки хранятся централизованно. Операции вынесены в `transactions`, так как это история первичных финансовых событий. История цен и валюты вынесены в отдельные таблицы. `currencies` обеспечивает справочную целостность кодов валют. Для импортов предусмотрены партии и строки предварительной проверки. ML-подсистема разделяет метаданные моделей, запуски обучения и результаты прогнозирования или кластеризации. Целостность планируется обеспечивать первичными, внешними и уникальными ключами и проверками, а доступ к данным — через PL/SQL-процедуры Oracle.

Типовые вопросы преподавателя и позиции:

- **Почему много таблиц?** Каждая описывает самостоятельную сущность/процесс, уменьшает дублирование и повышает целостность. Число 21 — следствие выбранной модели, не самоцель.
- **Почему `instruments` отдельно от `assets`?** Инструмент общий, позиция зависит от конкретного портфеля.
- **Почему `transactions` отдельно от `assets`?** Операции нужны для пересчёта истории, доходности и налогов.
- **Зачем `currencies`?** Валидация существующих кодов валют и два внешних ключа для исходной/целевой валюты курсов.
- **Почему `exchange_rates` без FK к каждой транзакции?** Подбор курсов по дате/валютной паре — вычисление; связь с валютами структурная, с транзакциями не требуется.
- **Зачем три таблицы ML?** Метаданные алгоритма, запуск/обучение, результат применения. Обученная модель — объект Oracle.
- **Какая нормальная форма?** Преимущественно нормализованная структура, но вычисляемые значения и кэши — осознанная денормализация под скорость запросов; точную НФ надо обосновать отдельно.
- **Как будет работать Avalonia?** Через C# адаптер, вызывающий PL/SQL API; бизнес-логика переносится в Oracle.
