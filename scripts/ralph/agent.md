# Контракт итерации

Выполни только переданную задачу. Сначала прочитай AGENTS.md, если он существует в применимых каталогах, docs/oracle-requirements.md, релевантные docs/adr/ и сценарии из docs/spec/use-cases.md. Схема — docs/spec/er-model.drawio, задание — docs/spec/assignment.docx. Исторический контекст docs/spec/previous-context.md открывай только при необходимости: более поздние решения из oracle-requirements.md имеют приоритет.

Сначала абстракция, затем конкретная реализация. Переиспользуй подходящие интерфейсы. Репозитории Oracle вызывают процедуры, адаптеры источников скрывают формат поставщика. Бизнес-правила, расчёты и авторизация принадлежат Oracle. C# отвечает за UI, вызовы серверного API, интеграции и файловый транспорт. ACID, SOLID, DRY, KISS и YAGNI применяются без лишних слоёв.

Для Oracle прочитай ~/.codex/skills/oracle-db/SKILL.md и нужные разделы. Для C# прочитай ~/.codex/skills/csharp-expert/SKILL.md; для рефакторинга — csharp-refactoring, для новых тестов — code-testing. При любой работе с UI обязательно прочитай ~/.agents/skills/impeccable/SKILL.md, выполни его setup и используй существующие Avalonia-токены и компоненты. Не переноси WPF/web API в Avalonia механически. Для Go сначала golang-how-to. Если обязательный скилл недоступен, верни needs_user, не устанавливай его молча.

Срез должен давать проверяемое поведение по всем необходимым слоям. Не оставляй заглушек вместо финансовых формул, моков вместо реального Oracle или скрытой второй реализации расчёта в C#. Сохраняй работоспособность остальных сценариев. PostgreSQL может временно существовать для ещё не перенесённых сценариев; для перенесённого сценария источник истины один. Не ослабляй и не удаляй тесты ради зелёного результата.

Не меняй согласованную ER без отдельного разрешения пользователя: при необходимости опиши противоречие, минимальное изменение и вариант без него; верни needs_user. Аналогично поступай при отсутствии ключей, Docker-доступа, неподтверждённых правил РБ или необходимости нового продуктового решения. Не имитируй успешные проверки. Невозможность выполнить обязательную проверку — needs_user, не completed.

Не меняй backlog, скрипты/промпты цикла, требования, ADR и .ralph. Для передачи знаний приложи evidence и next_steps в ответе; они сохраняются между итерациями. Коммиты после каждой изменившейся итерации и push выполняет runner; исполнитель оставляет изменения для его проверки. Не делай git commit/push/reset/clean, не публикуй ничего, не удаляй volumes, не запрашивай чужие данные. Не выводи секреты. Не трогай посторонние изменения. Комментарии только при необходимости: с маленькой буквы по-русски, естественным языком разработчика.

Для экономии контекста исследуй текущий путь вызовов, а не весь репозиторий; повторно читай только изменившиеся документы. Используй небольшие целевые проверки до одной итоговой проверки среза. Работай в этом процессе без вложенных агентов, если задача прямо не требует делегирования. Завершённые критерии подтверждай краткими ссылками на файлы и логи вместо длинных пересказов.

Выполни проверки задачи, добавь соразмерные проверки бизнес-поведения и реальные интеграционные проверки Oracle. Для UI приложи визуальные свидетельства; сборка не доказывает качество UI. В evidence укажи команды и результаты, пути к артефактам, покрытые критерии. completed допустим только при выполнении всех критериев; retry — если остаётся работа, которую следующая итерация может продолжить без пользователя; needs_user — если требуется решение или доступ.
